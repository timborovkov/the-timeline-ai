The Timeline runs as a set of Railway services in one project, all built from this monorepo.

Services

worker App apps/worker/railway.json (Railpack) NODE_ENV=production node apps/worker/dist/index.js

Railway provisions PostgreSQL and Redis from database templates. They remain customer-operated services rather than managed databases. Qdrant and RustFS are deployed as custom services using their official Docker images. Portable app Dockerfiles live under docker/ for local/container-platform builds; keep the repo root free of an app Dockerfile so Railpack follows the service railway.json files.

Initial setup

  1. Create Railway project linked to this GitHub repo.
  2. Add the PostgreSQL template. Inject its connection string as DATABASE_URL.
  3. Add the Redis template. Inject its connection string as REDIS_URL.
  4. Add Qdrant service: New Service → Docker Image → qdrant/qdrant:v1.12.4. Persistent volume at /qdrant/storage. Set QDRANT__SERVICE__API_KEY to a strong random value.
  5. Add RustFS service: New Service → Docker Image → rustfs/rustfs:latest. Persistent volume at /data. Set RUSTFS_ROOT_USER and RUSTFS_ROOT_PASSWORD. Bucket creation: run mc commands once after first deploy (below).
  6. Add web service from this repo, pointing at apps/web/railway.json.
  7. Add the worker service from this repo, pointing at apps/worker/railway.json.
  8. Add the document-extract-orchestrator service from this repo. In Railway's service settings, set the custom config path to /apps/worker/railway.extract.json (credential-thin document-extract consumer — ADR 0013).

On the main worker, set DOCUMENT_EXTRACT_ENABLED=false so only document-extract-orchestrator consumes that queue. On document-extract-orchestrator, set WORKER_MODE=document-extract, DAYTONA_API_KEY, OPENROUTER_API_KEY, DATABASE_URL, REDIS_URL, and S3 document-bucket variables. Set OPENROUTER_GUARDRAIL_ID and the generated OPENROUTER_PRIVACY_POLICY_ATTESTATION only after an operator-only management-key check verifies the exact inference-key assignment, model allowlist, guardrail/ZDR settings, and account privacy settings. Never add the management key to Railway runtime variables. See OpenRouter setup for the generation command. Set DAYTONA_SNAPSHOT=auto to resolve the content hash from document-extract-sandbox/ for each deployed revision. Do not set SECRETS_ENCRYPTION_KEY, Auth secrets, or Telegram/Slack/integration OAuth tokens on document-extract-orchestrator. Snapshot lifecycle (CI ensure, manual deployed-hash-aware retention, sandbox-aware pruning, and optional boot create-once): ADR 0013 and pnpm --filter @timeline/worker create-document-extract-snapshot.

Push CI never prunes snapshots because an idle deployed extractor has no persistent Daytona sandbox reference. Use the snapshot workflow's manual deployed_snapshots input only after collecting the active hash from every production/staging extractor's successful document-extract Daytona snapshot ensured startup log. The cleanup keeps those deployed hashes plus the current and two rollback hashes and fails closed when the inventory is absent or stale. Do not set DAYTONA_ACTIVE_SNAPSHOTS as a Railway service variable; it is a maintenance-command input only.

Extract startup checks the raw environment against a strict credential-thin allowlist. Railway's normal Railpack / MISE runtime variables are accepted automatically. If startup reports an unexpected variable, remove that copied service variable or deliberately add an exact non-secret platform key in code; do not widen the allowlist by prefix.

The worker then refreshes typing and delivers durable Telegram answers after the request has returned. Slack worker delivery needs no plaintext bot-token variable because it decrypts the installed workspace token from Postgres with SECRETS_ENCRYPTION_KEY.

AUTH_URL is also the canonical public origin. Requests that arrive through www.thetimeline.cc or the default *.up.railway.app host are redirected to this origin before Auth.js runs.

Railway uses the checked-in Railpack manifests for web and worker deploys. The Dockerfiles are kept for local production-parity runs and now accept the same Sentry build/runtime variables, but Railway source-map upload depends on the variables above being available at build time in each Railway service.

Keep NODE_ENV set to production in both staging and production Railway environments. Use Railway's environment name and SENTRY_ENVIRONMENT for labels such as staging; Node.js and the app env schema only accept development, test, or production.

Production env validation rejects LANGSMITH_TRACING=true because rich traces can include private prompt and output content. Use LangSmith only in controlled development or evaluation environments with synthetic or explicitly approved data. The hosted production OpenRouter key must be restricted to the code-owned model catalog with applicable ZDR guardrails for every zdr_required role. Production also requires OPENROUTER_GUARDRAIL_ID and the generated OPENROUTER_PRIVACY_POLICY_ATTESTATION. The token invalidates on inference-key, guardrail, catalog, or policy drift; it does not create or prove the provider settings. Verify the actual key assignment, allowed_models, and guardrail settings with a separate operator-only management-key deployment check and dated evidence. Never store the management key in web, worker, or document-extract runtime variables. The voice-transcription role remains the separately disclosed retained, no-training quality exception.

Use Railway's "shared variables" feature at the project level for anything used by 2+ services (everything except service-local overrides).

About S3_PUBLIC_ENDPOINT: the browser uploads voice notes, document files, and fetches audio for playback directly against this URL, so it must be publicly reachable over HTTPS. Expose the RustFS service via a Railway public domain (Settings → Networking → Generate Domain) and set S3_PUBLIC_ENDPOINT to that URL. S3_ENDPOINT stays on the private network — workers and server-side code keep using it.

About TURNSTILE_*: Turnstile is used only on anonymous abuse surfaces: email/password registration and the public support/contact form. OAuth signup and signed-in product flows rely on Redis-backed rate limits, team permissions, and existing quota checks. In production, leave neither key blank; the server action rejects missing or invalid Turnstile tokens.

Staging vs production

Two Railway environments on the same project: staging and production. Each gets its own Postgres, Redis, Qdrant, RustFS instances. Domains:

  • staging.thetimeline.cc → staging web
  • thetimeline.cc → production web

Branch deploys: main → production, staging → staging. Configure via Railway service settings.

Volumes and persistence

Critical: Qdrant and RustFS must have persistent volumes attached. Railway services without volumes lose data on every deploy. Set these up at service creation time — adding volumes later is more painful.

Service Mount path Sized for
Qdrant /qdrant/storage Start 10GB. Grows with vector count.
RustFS /data Start 50GB. Grows with audio/attachments.

PostgreSQL and Redis are Railway database templates rather than managed database services. Timeline remains responsible for their operation, persistence, backup configuration, and restore verification. Record the deployed volume and backup settings for each environment.

RustFS bucket initialization

After first RustFS deploy, create buckets. Run once per environment:

mc alias set timeline-prod http://<rustfs-host>:9000 <user> <password>
mc mb timeline-prod/timeline-audio
mc mb timeline-prod/timeline-attachments
mc mb timeline-prod/timeline-exports
mc mb timeline-prod/timeline-documents
mc version enable timeline-prod/timeline-audio
mc version enable timeline-prod/timeline-attachments
mc version enable timeline-prod/timeline-documents
mc version enable timeline-prod/timeline-exports

Versioning on audio, attachments, and documents is non-negotiable. Source-of-truth data; never overwrite blindly.

Backups

Do not assume a PostgreSQL backup exists from the template alone. Enable and inventory the production backup mechanism, record its schedule and retention, and prove a restore in an isolated environment before making a durability claim. The current repository cannot verify the deployed Railway dashboard state.

RustFS backup is an operating task, not a shipped repository guarantee. After choosing the secondary store, set up a scheduled service (Railway cron), for example: 

rclone sync s3:timeline-audio backblaze-b2:timeline-backup-audio
rclone sync s3:timeline-attachments backblaze-b2:timeline-backup-attachments
rclone sync s3:timeline-documents backblaze-b2:timeline-backup-documents
rclone sync s3:timeline-exports backblaze-b2:timeline-backup-exports

Backblaze B2 or any cheap S3-compatible store works. Test restores quarterly.

Qdrant snapshots are also an operating task. Add a nightly job through Qdrant's snapshot API and upload the result to an independently protected store such as B2. Vector data can be regenerated by re-embedding source records, but a tested snapshot avoids that cost when the only failure is Qdrant data loss.

  • Google Drive: https://thetimeline.cc/api/webhooks/google-drive
  • Linear: https://thetimeline.cc/api/webhooks/linear
  • GitHub App: https://thetimeline.cc/api/webhooks/github
  • Monday.com: https://thetimeline.cc/api/webhooks/monday?token=<MONDAY_WEBHOOK_SECRET>
  • Sentry native integration: https://thetimeline.cc/api/webhooks/sentry
  • Ingest webhooks: https://thetimeline.cc/api/webhooks/ingest with Authorization: Bearer tli_..., or the secret URL copied from /app/sources.

Native integration OAuth callbacks also land on the web service, including /api/integrations/google_drive/callback, /api/integrations/linear/callback, /api/integrations/github/callback, /api/integrations/monday/callback, /api/integrations/slack/callback, and /api/integrations/sentry/callback.

The Telegram webhook and / command menu are registered automatically by the web service on startup. The Next.js instrumentation hook at apps/web/src/instrumentation.ts runs once per server process. If TELEGRAM_BOT_TOKEN is set, it calls setMyCommands for the default, private-chat, and group-chat scopes so Telegram clients can list bot commands when someone types /. In production it also reads TELEGRAM_WEBHOOK_SECRET and AUTH_URL, then always calls setWebhook (idempotent; required to push a rotated secret since getWebhookInfo doesn't expose Telegram's stored secret) and verifies via getWebhookInfo. Both calls are fire-and-forget so they never block readiness. Missing env vars → it logs a skip line and continues.

To register manually (e.g. from a laptop pointed at staging):

curl -X POST "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/setWebhook" \
  -d "url=https://thetimeline.cc/api/telegram/webhook" \
  -d "secret_token=$TELEGRAM_WEBHOOK_SECRET" \
  -d "allowed_updates=[\"message\",\"edited_message\",\"callback_query\"]"

The web service verifies the X-Telegram-Bot-Api-Secret-Token header on every request and rejects anything that doesn't match.

Ingest webhook credentials are managed in the dashboard and stored as database hashes, so Railway does not need a per-source env var. Rotate or disable them from Connections; new deliveries fail immediately after revocation.

Deploy flow

  1. Push to main (production) or staging branch.
  2. Railway builds each app service with Railpack using the service's railway.json build command. The build installs the full pnpm workspace, so operational scripts are available in railway ssh. The web build and deploy images run with NODE_ENV=production; deploy commands use node directly because Corepack's pnpm shims are not active there. The @timeline/web build also runs apps/web/scripts/prepare-standalone.mjs, which copies .next/static, public, and the shared dist/messaging/email-templates runtime assets into both the standalone root and app subtree so Railway serves the hashed CSS, JavaScript chunks, connector icons, self-hosted fonts, and outbound email templates.
  3. Migrations: run as a release-phase pre-deploy command on both app services. They also run from the web start wrapper and worker startup under the same Postgres advisory lock, so a web and worker deploy can overlap safely and each service can recover from an independent restart. The pre-deploy command is already wired in apps/web/railway.json and apps/worker/railway.json: 
    "preDeployCommand": [
  "NODE_ENV=production node packages/db/dist/migrate.js"
]
    The script (packages/db/src/migrate.ts) is built before deploy, and the Railpack runtime keeps the workspace files and installed dependencies available to the release command. The same migrate entrypoint is called by apps/web/start.mjs before apps/web/server.js and by apps/worker/src/index.ts before queues start consuming jobs. It applies any new SQL files against DATABASE_URL and exits; failure blocks deploy or startup. Startup migrations make dev resets and service-only redeploys converge on the next app boot even when the other service is not redeployed.

    The worker still calls waitForMigrations() from @timeline/db/wait-for-migrations after the migrator returns. That readiness check polls drizzle.__drizzle_migrations until the row count matches the journal bundled with the worker image. Default timeout 5 minutes. This catches skipped release commands or mismatched images before background queues start using a schema they do not have.

    Postgres pool guardrails. Shared clients set application_name labels (timeline-web, timeline-worker, timeline-migrator, timeline-migration-waiter, timeline-reset, or timeline-script) so pg_stat_activity shows which service owns a lock. App pools use a 10 second lock_timeout, 120 second statement_timeout, and 60 second idle_in_transaction_session_timeout; migration sessions keep the short lock wait but get a 10 minute statement budget. A deploy that is blocked behind an old lock should fail clearly instead of waiting indefinitely.

    SSL note. Inside a Railway project, DATABASE_URL resolves to the PostgreSQL service's internal hostname and uses plain TCP. If you ever point this at the external Postgres proxy (e.g., to run pnpm db:migrate from your laptop against staging), append ?sslmode=require to the URL — postgres-js follows the connection string, not an out-of-band env var.

  4. Legal-version release warning. Changing the current Terms or Privacy version intentionally makes every existing human session stale. Signed-in app and invite routes redirect to /legal/accept; human product APIs return a no-store 428 legal_acceptance_required response until the person accepts. Before a version bump, publish and review both documents, notify support and API consumers, and confirm the immutable acceptance-history migration is deployed. Service webhooks, cron jobs, health checks, inbound email, calendar feeds, and bearer-authenticated outbound MCP remain exempt because they cannot complete human clickwrap.
  5. Services restart with new image. Healthcheck on web (/api/health) must pass before traffic shifts.
  6. Workers restart with same image — they share the codebase, just different entry points.

Cost considerations

Railway charges per resource (CPU, RAM, network egress, volume size). At small scale this stack is roughly:

  • web service: small instance, mostly idle outside webhook spikes
  • worker service: small instance, most cost is during processing bursts
  • Postgres: small instance + storage
  • Redis: tiny
  • Qdrant: moderate RAM (vectors live in memory)
  • RustFS: minimal compute, most cost is volume size

Watch volume sizing — Railway storage is more expensive than the compute. For prod beyond a few teams, consider moving RustFS data to a cheaper external S3-compatible store (Backblaze B2, Cloudflare R2) and using RustFS only as a self-host fallback or dev convenience.
