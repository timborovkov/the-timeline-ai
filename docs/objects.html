Workspace objects

ArchitectureLast updated 2026-05-22

Phase 8 turned entities from an extraction artifact into the workspace's durable object model. Every deal, task, follow-up, decision, person, document, and incident a team tracks lives in the same table, behind the same withTeam scope, with the same agent tools, with one immutable audit trail.

What changed

Before Phase 8 the timeline was searchable memory — capture events, extract facts, resolve entities, ask the agent. Useful, but passive. Teams couldn't say "this is a deal", "I own this", "due Thursday", "blocked by that". Phase 8 keeps the timeline as the substrate and layers an object relation management system on top. Not just CRM for customers; the same model holds projects, vendors, incidents, hiring loops, decisions, and tasks.

Everything routes through withTeam(db, teamId, userId) — the single chokepoint for team isolation. The new objects module composes on top of TeamScope rather than replacing it.

Data model

entities was widened in place. Existing rows default safely (status='open', agent_suggested=false, archived_at=NULL), and the resolver keeps using the same canonical-name lookup it always has.

Table Purpose Key columns
entities (extended) Workspace objects of any kind. status, stage, priority, owner_user_id, assignee_user_id, due_at, source_event_id, agent_suggested, archived_at
entity_relationships Explicit, human/agent-authored links between objects. (from_entity_id, to_entity_id, kind) unique; kinds: parent, child, related, blocks, blocked_by, duplicate_of, linked
object_changes Immutable audit log — one row per modified field per save. actor_kind (user/agent/system), status (applied/suggested/rejected), previous_value, new_value, source_event_id
object_notes Mutable, author-owned notes attached to an object. author_user_id, body, soft deleted_at
object_views Per-user, per-object last-visit timestamp. Drives "since your last visit". PK (team_id, user_id, entity_id)
board_views Saved kanban/table/list configurations with JSON filter + groupBy. kind, filter (jsonb), group_by, is_shared
notifications In-app inbox. v1 fan-out is in-process inside updateObject. kind, entity_id, object_change_id, summary, read_at
chat_sessions Persisted conversations, optionally pinned to an object. created_by, pinned_entity_id, archived_at
chat_messages One row per role transition. content is structured JSON. session_id, role, content (jsonb)

Object types

The Postgres enum entity_type is the single source of truth. Use objects.OBJECT_TYPES at runtime and objects.ObjectType at the type level — derived from the drizzle enum so adding a new type requires only a schema + migration change.

Origin Types Naming uniqueness
Extraction-derived person, company, project, topic, other, vendor, document, decision Case-insensitive unique per (team, type, name). The resolver re-uses canonical names across captures.
User-authored work task, follow_up, deal, incident, hiring_loop Excluded from the uniqueness predicate. Teams legitimately reuse names ("follow up with Acme").

Status, stage, priority, due

Status vocabularies are free-form text, validated at the app layer because they differ by type. The UI ships per-type dropdowns:

Type Status options (default)
deal open · qualified · proposal · won · lost
task suggested · todo · doing · done · blocked · cancelled
follow_up todo · doing · done · cancelled
project planning · active · on_hold · shipped · cancelled
incident open · mitigated · resolved · postmortem
hiring_loop sourcing · interviewing · offer · hired · closed
decision draft · proposed · accepted · rejected
everything else open · active · archived

stage is opt-in (used by kanban boards), priority is a smallint 1–4 with 1 = urgent, and due_at is a tz-aware timestamp.

Audit trail

Every manual change — to an object's fields, to its notes, to its relationships — writes two rows in one transaction: a system-source raw_events row (so the change appears on the team timeline) and one object_changes row per modified field (so the object page's "Recent changes" pane has structured data). The raw_events.id threads through both as source_event_id.

Why two writes per change. The timeline view treats events as the unit; the object page treats fields as the unit. One save updates both, atomically. raw_events stays append-only — even note edits write a new event with the new body.

Agent-proposed changes land as object_changes.status = 'suggested'. A human accepts (flips to applied and runs the update) or rejects (terminal). The rejected rows stay visible so agent quality is measurable over time.

Notifications

Inside updateObject, after the entity + audit writes commit, the helper inserts object_changed notifications for the owner and assignee (deduped, and skipping the actor themselves). Fan-out is in-process for v1; if volume grows, the same helper can switch to a notify BullMQ queue without changing callers.

The inbox view (/app/inbox) sorts by (read_at NULLS FIRST, created_at DESC) — backed by the notifications_team_user_inbox_idx index so unread-first queries are direct.

Since last visit

Each object page write a row to object_views when the current user opens it. The render computes newSinceLastVisit by counting object_changes and object_notes created after the user's previous last_visited_at, before stamping the new visit. Order matters — moving the visit-stamp ahead of the page read would zero the banner forever after the first load.

Persisted chat sessions

/api/chat accepts an optional sessionId in the request body. If absent, the endpoint auto-creates a session (optionally pinned to an object via pinnedEntityId) and returns the new id via the x-tl-session-id response header. On stream finalize, the endpoint persists the latest user turn and the assistant turn (text + tool calls + finish reason + usage + prompt version) into chat_messages — the delta only, since useChat re-sends the whole transcript on every request.

Persistence failures are warn-logged, not surfaced to the user — the assistant reply has already streamed by the time the write attempts.

Server-side helpers

All in packages/shared/src/objects/index.ts. Every public function takes a TeamScope; the helpers read scope.teamId and never accept it as a parameter — that's the chokepoint that keeps a caller typo from leaking across teams.

Agent tools

Phase 8 ships the data + helpers and the agent toolset in packages/shared/src/agent/tools.ts. Read-side tools get_object, list_objects, list_tasks, and recent_changes sit alongside the existing get_entity / search_timeline / list_events. Write-side tools suggest_task and propose_object_change never mutate entities directly — they record status='suggested' rows that a human accepts or rejects from the object page. The system prompt is at agent-v3-2026-05.
