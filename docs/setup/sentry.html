Sentry setup

SetupLast updated 2026-06-03

Optional locally. Strongly recommended before production.

Hook the web and worker services into Sentry for error tracking. The integration is wired in code and stays disabled when DSNs are blank.

1. Project

  1. Sign up at https://sentry.io.
  2. Create a project — platform next-js for web, node-express for worker.
  3. Copy the DSN.

Set in .env:

SENTRY_DSN=https://...@o0.ingest.sentry.io/0
NEXT_PUBLIC_SENTRY_DSN=https://...@o0.ingest.sentry.io/0
NEXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE=0
NEXT_PUBLIC_SENTRY_PROFILES_SAMPLE_RATE=0
SENTRY_ENVIRONMENT=development
SENTRY_TRACES_SAMPLE_RATE=0
SENTRY_PROFILES_SAMPLE_RATE=0

2. Wiring

The web service initializes Sentry from the Next.js instrumentation files and routes browser events through /sentry-tunnel. The worker initializes @sentry/node on startup, captures fatal startup/shutdown errors, captures terminal BullMQ job failures after retries are exhausted, and flushes before exit.

App Router render boundaries, API route handlers, server actions, webhook background handlers, queue handoffs, and other caught-but-unexpected operational failures report to Sentry explicitly before returning graceful responses. Expected validation, authentication, not-found, rate-limit, and provider-noise outcomes stay out of Sentry.

Agent model runs, native tools, and custom MCP tool calls also report caught internal failures. Tool events include only the safe tool-name tag before returning tool_failed or a graceful reconnect shape to the model.

Keep sendDefaultPii disabled. Do not attach cookies, auth headers, prompts, transcripts, filenames, uploaded content, or raw document text to Sentry events. The scrubber removes request cookies and auth headers before send.

3. Source maps

The web build uploads Next.js source maps through withSentryConfig. The worker build runs sentry-cli sourcemaps inject and sentry-cli sourcemaps upload for apps/worker/dist, packages/shared/dist, and packages/db/dist. Set these only in CI/deploy environments that should upload source maps, and make sure they are available at build time, not only runtime: 

SENTRY_AUTH_TOKEN=
SENTRY_ORG=
SENTRY_PROJECT=
SENTRY_RELEASE=

SENTRY_RELEASE is optional because injected debug IDs are enough for source-map matching, but setting it to the deployed git SHA makes Sentry releases easier to audit. Without the first three values, the worker upload script logs a skip and local builds still succeed.

4. Production alerting checklist

  • Set SENTRY_DSN on the web and worker services, and NEXT_PUBLIC_SENTRY_DSN on the web service for browser errors.
  • Set SENTRY_ENVIRONMENT to the deployment label you want alerts grouped by, such as production.
  • Configure issue alerts and notification destinations in the Sentry project UI. The repo sends events; Sentry decides whether they page, email, or post to Slack.
  • Set SENTRY_AUTH_TOKEN, SENTRY_ORG, and SENTRY_PROJECT in CI/deploy build environments that should upload source maps.
