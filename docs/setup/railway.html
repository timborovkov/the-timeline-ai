Railway deployment setup

SetupLast updated 2026-10-24

Project + environment provisioning for staging and production. For the full service architecture see docs/railway.html.

The repo ships ready-to-deploy railway.json files for web and worker. Provisioning the Railway project is a manual step.

1. Project + environments

  1. Create a new Railway project.
  2. Use the default production environment. The current project has no users and uses this environment for development and deployment verification.
  3. Settings → Git — connect the repo. Branch deploys:
    • main → production

A separate staging environment is optional. If introduced, provision isolated services and credentials for release validation.

2. Database templates

Add via + New → Database:

  • PostgreSQL — Railway database template. Copy DATABASE_URL from the service's Connect tab into the project's shared variables.
  • Redis — Railway database template. Copy REDIS_URL likewise.

3. Custom services

Add via + New → Empty Service (or Deploy from Docker Image):

  • qdrant — image qdrant/qdrant:v1.20.0, attach a persistent volume at /qdrant/storage. Expose port 6333. Set QDRANT__STORAGE__SNAPSHOTS_PATH=/qdrant/storage/snapshots so backups persist. Set QDRANT__SERVICE__API_KEY to a random value; copy to shared QDRANT_API_KEY. Set shared QDRANT_URL to the service's private URL. New collections keep original vectors and payload on disk and pin int8 quantized vectors in RAM; file cache, indexes, and runtime allocations also consume memory. Size the limit from measured startup, search, and ingestion peaks. Production uses an initial 2 vCPU / 3 GB RAM limit with the rollback collection retained; see the production memory measurements. Smaller demo corpora need their own measurements before selecting a lower limit. Alternatively, point staging/prototypes at Qdrant Cloud's free tier (1 GB RAM, 0.5 vCPU, 4 GB disk, no credit card). Do not use that free cluster for production: it is a single node, has no high availability, and unused clusters are suspended after a week. Copy an existing in-RAM collection with bun run --filter @timeline/worker qdrant-migrate-collection before lowering a Railway memory limit; the procedure is in OpenRouter setup.
  • rustfs — image rustfs/rustfs:latest, attach a persistent volume at /data. Set RUSTFS_ACCESS_KEY/RUSTFS_SECRET_KEY. Map env to S3_ACCESS_KEY_ID/S3_SECRET_ACCESS_KEY in shared variables.

Configure explicit CPU and RAM limits for every service, including web and workers. The production resource-cap table records the current limits and sampled memory peaks. Reassess before bulk maintenance or larger workloads; development and staging need their own capacity checks.

Run a one-shot rustfs/rc:v0.1.36 job to create buckets (same commands as rustfs-init in docker-compose.yml).

4. App services

Add web, worker, and document-extract-orchestrator services pointing at this repo. Use /apps/web/railway.json, /apps/worker/railway.json, and /apps/worker/railway.extract.json respectively as each service's custom config path. All three select the repository Dockerfiles, which install the frozen Bun workspace and compile the packages they run. App services also run the shared DB migrator in preDeployCommand; the advisory lock makes overlapping deploys safe. Portable app Dockerfiles live in docker/; do not add a root Dockerfile for these services.

Bun is pinned to 1.4.4 in .bun-version, package.json, and the Debian-based Dockerfiles. Railway uses the repository Dockerfiles for all three application services; remove old Railpack build commands and Node start-command overrides. See the migration and rollback runbook.

The document-extract-orchestrator service is the credential-thin document-extract consumer (ADR 0013). Set WORKER_MODE=document-extract, DAYTONA_API_KEY, OPENROUTER_API_KEY, DATABASE_URL, REDIS_URL, and S3 document-bucket variables. Set OPENROUTER_GUARDRAIL_ID and the generated OPENROUTER_PRIVACY_POLICY_ATTESTATION only after an operator-only management-key check verifies the exact inference-key assignment, model allowlist, guardrail/ZDR settings, and account privacy settings. Never add the management key to Railway runtime variables. See OpenRouter setup for the generation command. Set DAYTONA_SNAPSHOT=auto so each deployed extractor resolves its matching content hash. DAYTONA_SNAPSHOT_ENSURE=true (default) create-once if missing; it does not rebuild every restart. Push CI never deletes snapshots: idle deployed extractors have no persistent Daytona sandbox to reveal the hash they still need. For manual cleanup, pass every production/staging deployed hash as the workflow's deployed_snapshots input (or DAYTONA_ACTIVE_SNAPSHOTS locally). Collect each hash from that environment's successful orchestrator startup log entry (document-extract Daytona snapshot ensured) before dispatching cleanup. Cleanup keeps those hashes plus the current and two rollback hashes, and skips any snapshot referenced by a sandbox. Do not set DAYTONA_ACTIVE_SNAPSHOTS, SECRETS_ENCRYPTION_KEY, Auth secrets, or Telegram/Slack/integration OAuth tokens on document-extract-orchestrator. On the main worker, set DOCUMENT_EXTRACT_ENABLED=false so only document-extract-orchestrator consumes that queue. Local/CI ensure: bun run --filter @timeline/worker create-document-extract-snapshot.

Extract startup enforces a raw-env allowlist. The pinned Bun image runtime paths and explicitly listed Railway metadata are supported, but a copied app secret or unknown service variable intentionally stops the process. Remove the extra variable instead of sharing the web/worker variable group with document-extract-orchestrator.

5. Shared variables

In Settings → Variables, set everything from .env.example that isn't a local-only default. Mark provider tokens and secrets (OpenRouter, Telegram, Slack, Postmark, Sentry, and native integration OAuth client secrets such as GitHub, Linear, and Monday.com) as secret. PostHog's project key and host are not secrets, but keep them environment-specific. The independent ANALYTICS_PSEUDONYMIZATION_KEY is secret and must never be exposed to the browser.

TELEGRAM_BOT_TOKEN must be available to both app services. The web service owns webhook authentication and keeps the initial typing heartbeat active until the worker claims the durable conversation-agent job. The worker then owns the four-second typing refresh and final Telegram reply. Slack delivery reconstructs its worker adapter from encrypted installed-workspace tokens using SECRETS_ENCRYPTION_KEY, so do not add a separate Slack bot token variable.

Meeting capture also requires RECALL_API_KEY, RECALL_BASE_URL, RECALL_WORKSPACE_VERIFICATION_SECRET, and the optional transcript URL and display-name variables documented in the Recall.ai setup guide. Only older dashboard status endpoints use the legacy RECALL_STATUS_WEBHOOK_SECRET fallback. Hosted services must set TIMELINE_DEPLOYMENT_MODE=hosted and RECALL_RETENTION=1 (or leave retention empty, which resolves to one hour); env validation rejects longer or indefinite media retention in that hosted production mode. It also accepts only Recall's documented HTTPS regional /api/v1 endpoints and pins the transcript callback to AUTH_URL's origin plus /api/webhooks/recall/transcript with no query or fragment.

Keep CROSS_SOURCE_EVIDENCE_MODE=off until the environment has passed its shadow promotion gates. shadow records content-free evidence-pack metrics without changing generic ingest webhook proposals; enforced requires exact per-change citations for that adapter. Other proposal adapters remain unchanged. Changing this worker setting requires a worker restart or redeploy. Sampling runs persisted with --team retain the required scenario policy and promotion blocker codes; check the promotion badge in Team → Reconciliation rather than treating zero fixture failures as rollout readiness.

Keep NODE_ENV as production for both Railway environments. Use the Railway environment name and SENTRY_ENVIRONMENT for labels like staging; the app rejects NODE_ENV=staging. Set TIMELINE_DEPLOYMENT_MODE=hosted on every Timeline-operated Railway service.

Set AUTH_URL to the primary public origin, such as https://thetimeline.cc. The web proxy redirects alternate hosts, including www and Railway's default *.up.railway.app host, back to this origin before Auth.js runs.

Production security and rate-limit buckets trust only X-Real-IP. Keep Railway's public proxy as the only web ingress and verify that it overwrites or removes any caller-supplied X-Real-IP before forwarding the request. Never expose the web service through a path that preserves a client-provided value. If the trusted header is missing or invalid, production requests deliberately share the unknown bucket instead of trusting spoofable forwarding headers.

A self-hosted production deployment has the same contract: place a trusted reverse proxy in front of the web service, strip incoming X-Real-IP, and set a validated client address yourself. CF-Connecting-IP and X-Forwarded-For are accepted only during local development and are not production fallbacks.

Add OPENAI_APPS_CHALLENGE_TOKEN to the web service only when OpenAI's app-submission portal supplies a domain-verification token. Preserve the exact plain-text value: the web route returns it verbatim at /.well-known/openai-apps-challenge. This variable is optional, is not an OAuth credential, and is not needed by the worker or document extractor. Leave it unset outside the portal verification flow, or remove it once the portal no longer requires it.

For production abuse controls, also set TURNSTILE_SITE_KEY, TURNSTILE_SECRET_KEY, and SUPPORT_EMAIL. Turnstile is only rendered on anonymous public forms: email/password registration and /help/support. OAuth sign-up and signed-in app forms do not show CAPTCHA; they use rate limits, permission checks, and product quotas instead.

For personless surface counts and pseudonymous server/worker product analytics, set POSTHOG_PROJECT_KEY, POSTHOG_HOST=https://eu.i.posthog.com, and a separate high-entropy ANALYTICS_PSEUDONYMIZATION_KEY. Set NEXT_PUBLIC_POSTHOG_KEY and NEXT_PUBLIC_POSTHOG_HOST=https://eu.i.posthog.com only when the consent-gated public-browser path and provider account have been verified; leaving the public key empty disables browser capture. Put the server analytics values only on web and the main worker; the document-extract orchestrator does not emit product analytics and its startup allowlist rejects them. See Analytics setup. For error monitoring, set SENTRY_DSN, NEXT_PUBLIC_SENTRY_DSN, NEXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE, NEXT_PUBLIC_SENTRY_PROFILES_SAMPLE_RATE, SENTRY_ENVIRONMENT, SENTRY_TRACES_SAMPLE_RATE, SENTRY_PROFILES_SAMPLE_RATE, and optional source-map upload variables SENTRY_AUTH_TOKEN, SENTRY_ORG, SENTRY_PROJECT, and SENTRY_RELEASE. Source-map variables must be available during the Railway build phase for both the Next.js upload and worker sentry-cli upload.

Keep LANGSMITH_TRACING=false in hosted production. Env validation rejects production tracing because rich traces can include private prompt and output content. Use it only in controlled development or evaluation environments with synthetic or explicitly approved data. The production OpenRouter key must be restricted to the code-owned model catalog with applicable ZDR guardrails for every zdr_required role. Hosted production also requires OPENROUTER_GUARDRAIL_ID and the generated OPENROUTER_PRIVACY_POLICY_ATTESTATION. The token invalidates on inference-key, guardrail, catalog, or policy drift, but provider-side assignment and settings still require a separate management-key deployment check and dated evidence. Never deploy that management key to the app. The voice-transcription role remains the separately disclosed retained, no-training quality exception.

Keep LEGAL_PUBLICATION_READY=false until G-20 in the security/privacy/trust register is resolved and dated official registry evidence is retained. In production that default withholds the binding Terms, legal acceptance, and first-time account signup while preserving existing users' signed-in dashboard access. The true value is only an operator attestation after evidence exists, not a substitute for evidence. Once ready, a release that changes TERMS_VERSION or PRIVACY_VERSION forces existing people through /legal/accept and makes human product APIs return 428 legal_acceptance_required until acceptance. Publish and review the legal text before deploying that bump, brief support/API consumers, and verify the append-only acceptance migration first.

6. Healthchecks

Already configured in apps/web/railway.json → /api/health. Railway will restart the service on failure.

7. Job reconciler (optional cron)

Set CRON_SECRET in shared variables to enable POST /api/cron/reconcile. The endpoint re-enqueues stuck transcribe / extract / embed jobs for raw events idle past 15 minutes, and is idempotent because workers are deterministic on raw_events and Qdrant point ids. Run it from Railway's scheduler (or any cron service) every few minutes: 

curl -fsS -H "Authorization: Bearer $CRON_SECRET" \
  https://thetimeline.cc/api/cron/reconcile

Leave CRON_SECRET unset to disable the endpoint (returns 503). The handler also accepts GET for cron services that don't support POST bodies.

Dead-letter behavior. Each (row, stage) is re-enqueued at most 3 times. After that the reconciler stamps source_metadata.reconcile_giveup_<stage> with the giveup timestamp and skips the row on subsequent runs. The response payload includes a deadLettered count for dashboards. To retry a dead-lettered row manually, clear the giveup key from source_metadata: 

UPDATE raw_events
SET source_metadata = source_metadata
  - 'reconcile_giveup_transcribe'
  - 'reconcile_attempts_transcribe'
WHERE id = '<uuid>';
