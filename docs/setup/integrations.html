Native integrations & custom MCPs

SetupLast updated 2026-06-25

Connect native GitHub, Linear, Google Drive, Monday.com, Slack, and Sentry provider accounts from /app/me/connections, activate shared team sources from /app/team/integrations, or plug arbitrary custom MCP servers in at /app/team/mcp-servers. Native providers sync external activity into the timeline as source='integration'. MCP servers give the agent live tool access; they do not automatically create timeline events unless paired with a native sync adapter or custom ingestion layer. For tools that only need to push arbitrary evidence into Timeline, admins can also create named ingest webhooks from /app/team/integrations.

Encryption key (required first)

All integration auth (OAuth refresh + access tokens, bearer tokens, custom-header values, basic-auth credentials, MCP dynamic-client secrets) is encrypted at rest with AES-256-GCM in packages/shared/src/crypto/secrets.ts. Generate a 32-byte key and set SECRETS_ENCRYPTION_KEY in your environment: 

node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"

The first encryptSecret() call throws with a clear message if the key is missing or the wrong length, so worker boot fails fast instead of writing plaintext.

Google Drive

Timeline uses a server-side OAuth web flow and requests Drive read-only access. Google scopes are requested by the authorize URL, but the OAuth consent screen must be configured for external/internal use before non-test users can connect.

  1. In Google Cloud Console → APIs & Services → Credentials, create an OAuth 2.0 client with type Web application.
  2. Under Authorized redirect URIs, add: https://thetimeline.cc/api/integrations/google_drive/callback. Authorized JavaScript origins are not used by Timeline's server-side callback flow.
  3. Enable the Google Drive API for the project.
  4. Ensure the OAuth consent screen allows these scopes: https://www.googleapis.com/auth/drive.readonly and https://www.googleapis.com/auth/drive.metadata.readonly.
  5. Copy the OAuth client id and client secret from the credential details page.
  6. Set: 
    GOOGLE_CLIENT_ID=...
GOOGLE_CLIENT_SECRET=...
# REQUIRED before accepting Drive webhooks. 32+ bytes of randomness.
GOOGLE_DRIVE_WEBHOOK_SECRET=...
  7. Restart the web + worker services. The provider appears in the native catalog when the required credentials are configured.
  8. Any team member can connect their Google Drive account from /app/me/connections or the native catalog. The member chooses whether their My Drive root or shared drives are shared with the current Timeline team.
  9. A team admin activates shared Drive sources from /app/team/integrations.
  10. (Optional) Register a Drive push-notification channel for incremental sync. The channel token must be <integration_id>.<HMAC-SHA256(GOOGLE_DRIVE_WEBHOOK_SECRET, integration_id)>; route hits /api/webhooks/google-drive. The handler refuses inbound notifications when the secret is unset, and rejects bad signatures.

Linear

Timeline uses Linear OAuth plus an optional signed webhook. OAuth grants the connection owner read access; the team only activates Linear teams that owner shares.

  1. Create an OAuth application at linear.app/settings/api/applications.
  2. Redirect URI: https://thetimeline.cc/api/integrations/linear/callback.
  3. Grant the OAuth app the read scope.
  4. Copy the OAuth client id and client secret from the Linear application page.
  5. Set: 
    LINEAR_CLIENT_ID=...
LINEAR_CLIENT_SECRET=...
LINEAR_WEBHOOK_SECRET=...
  6. In Linear Settings → API → Webhooks, point the webhook at https://thetimeline.cc/api/webhooks/linear with the secret above.
  7. Any team member can connect Linear from /app/me/connections or the native catalog. The member chooses which Linear teams are shared with the current Timeline team.
  8. A team admin activates shared Linear teams from /app/team/integrations.

GitHub

GitHub is a native Timeline integration. It is optional for non-engineering teams, but when connected it receives the same first-party treatment as Linear and Google Drive: person-owned OAuth, team source selection, audit rows, encrypted tokens, worker sync, and cited timeline events. Synced external work items can also map to task objects; visible task titles stay human-facing while provider IDs, issue keys, numbers, and URLs stay in integration metadata, aliases, or evidence.

  1. Create an OAuth App at github.com/settings/developers. For an organization-owned app, use the organization's Settings → Developer settings page instead.
  2. Callback URL: https://thetimeline.cc/api/integrations/github/callback.
  3. Timeline requests scopes in the OAuth authorize URL, so there is no separate scope picker on the GitHub OAuth App page. The requested scopes are repo and read:org.
  4. If you configure Timeline with a GitHub App client, grant repository read permissions for Contents, Issues, Pull requests, Actions, and Metadata. Missing Pull requests read access records a PR-surface partial sync on the /pulls endpoint while commits, issues, releases, and workflow runs continue to sync when readable.
  5. Copy the OAuth app Client ID and generate/copy a Client secret.
  6. Set: 
    GITHUB_APP_CLIENT_ID=...
GITHUB_APP_CLIENT_SECRET=...
  7. Any team member can connect GitHub from /app/me/connections or the native catalog. The member then chooses which repos or organizations are shared with the current Timeline team.
  8. A team admin activates shared sources from /app/team/integrations. A GitHub organization scope means all repos in that org the connection owner can access, including future repos; choose individual repos instead for a fixed list.
  9. Selected GitHub sources are synced by the integration worker poller; no repo/org webhook setup is required. After a successful sync, GitHub background polling runs on a slower cadence than the global integration tick to protect the connection owner's GitHub API quota.

Monday.com

Timeline uses monday.com's OAuth app flow, not a marketplace-only integration recipe. The app needs read scopes for boards, users, updates, and WorkDocs so selected boards and docs can become cited Timeline evidence.

  1. Open monday.com Developer Center, create an app, and open its OAuth / Permissions settings.
  2. Add the redirect URI: https://thetimeline.cc/api/integrations/monday/callback.
  3. Add these OAuth scopes exactly: boards:read, users:read, updates:read, and docs:read. Timeline also sends the same space-separated scope list in the OAuth authorize URL.
  4. Copy the app's Client ID and Client Secret from the Basic Information / OAuth settings.
  5. Set: 
    MONDAY_CLIENT_ID=...
MONDAY_CLIENT_SECRET=...
  6. Any team member can connect Monday.com from the native catalog. The member chooses which boards and WorkDocs are shared with the current Timeline team.
  7. A team admin activates shared sources from /app/team/integrations. The integration worker imports board schema, generic records, subitems, record updates, status changes, owners, column changes, and selected WorkDocs into cited timeline events.

Slack workspace ingestion

Slack has two first-party modes. Conversational capture handles DMs, bound-channel capture, /ask, and /timeline join. Native workspace ingestion uses the same Slack app credentials but syncs selected channels as a passive integration with source='integration' and provider='slack'.

  1. Configure the Slack app from Slack conversational capture setup, including SLACK_CLIENT_ID, SLACK_CLIENT_SECRET, and SLACK_SIGNING_SECRET.
  2. Add the native ingestion redirect URI: https://thetimeline.cc/api/integrations/slack/callback.
  3. Ensure the bot scopes include the native-ingestion scopes: channels:read, channels:history, groups:read, groups:history, files:read, reactions:read, users:read, and users:read.email. The conversational Slack setup page also lists the additional scopes/events needed for commands, DMs, reactions, and app mentions.
  4. Connect Slack from the native catalog, share selected channels from /app/me/connections, then activate them from /app/team/integrations. Private channels require the bot to be present before Slack will expose history.

Sentry native source

These credentials are separate from SENTRY_DSN. Timeline uses Sentry OAuth to read selected Sentry organizations/projects into Timeline; it does not change where Timeline reports its own application errors.

  1. In Sentry, open Account Settings → API → Applications and create an OAuth application for Timeline.
  2. Add the redirect URI: https://thetimeline.cc/api/integrations/sentry/callback.
  3. Sentry OAuth scopes are requested by Timeline in the authorize URL; the app page may not have a separate scope picker. Timeline requests org:read, project:read, event:read, event:admin, and team:read.
  4. Use a confidential/server-side OAuth app that exposes a client secret. If the page says Public Client and only shows a client id, that PKCE-only app is not compatible with the current Timeline provider until the Sentry adapter adds PKCE support.
  5. Copy the Client ID and Client Secret. Authorized JavaScript origins are not used by Timeline's server-side callback flow.
  6. Set: 
    SENTRY_INTEGRATION_CLIENT_ID=...
SENTRY_INTEGRATION_CLIENT_SECRET=...
  7. Connect Sentry from the native catalog, share selected projects from /app/me/connections, and activate them from /app/team/integrations. Timeline imports issue updates, resolved issues, and releases as cited events; Sentry issues map to Timeline incident objects.

Native provider ownership

Native provider credentials are provider connections: they belong to the team member who completes OAuth, not to the Timeline team. The team owns only the active source scope it has chosen from the resources that owner shared. Non-owners cannot browse private provider resources that have not been shared with the team.

If a connection owner leaves the team, deletes a connection, or GitHub, Drive, Linear, Monday.com, Slack, or Sentry requires reconnecting, Timeline creates connection attention. The team integrations page shows an attention banner and the affected provider groups so admins can ask the owner to reconnect, replace a connection with another shared source, or narrow shared sources; the worker pauses only the affected sync path and keeps previously captured raw events.

Ingest webhooks

Ingest webhooks are named evidence-only sources for arbitrary provider payloads: JSON, XML, text, form bodies, or any other text-like content. They do not require a provider-specific schema and never become authoritative state by themselves; the AI extraction pipeline can turn them into facts, citations, embeddings, and approval proposals.

  1. Go to /app/team/integrations as a team admin.
  2. Create a named webhook, for example Pipedrive webhook. Choose whether new events default to team-visible evidence or private evidence owned by the creating admin.
  3. Copy the one-time secret URL or bearer token. Plaintext credentials are shown once; stored credentials are SHA-256 hashes and can be rotated without changing the webhook source.
  4. Configure the third-party provider to send POST requests to the copied URL. Providers that cannot store the key in the URL can call /api/webhooks/ingest with Authorization: Bearer tli_....
  5. Keep proposal generation enabled when the source may contain task, date, object, or relationship evidence. Disable it when the source should only land searchable evidence. The worker checks the current setting again before processing queued proposal jobs.

The public endpoint rate-limits both authentication attempts and accepted deliveries, dedups identical same-day deliveries per webhook, redacts sensitive request headers from metadata, enforces the payload size cap while reading the request body, and rejects binary/multipart uploads for now. Payload text is fenced as external content before extraction and proposal prompts, so sender-authored instructions remain evidence instead of agent instructions. Documents and rich files should still go through the document drive until binary webhook ingestion is intentionally designed.

Custom MCP servers (inbound)

Bring tools from any MCP-compatible server into the agent's toolset. Visit /app/team/mcp-servers (team catalog — admins only) or /app/me/mcp-servers (personal overlay — visible only to you, any member can add). MCP servers are queried on demand during chat; they are not passive ingestion jobs and do not write provider activity into raw_events. Pick an auth mode:

  • None — public MCP servers with no auth.
  • Bearer token — API keys / personal access tokens.
  • Custom header — arbitrary header name + value.
  • OAuth — server speaks the MCP OAuth dance; state JWT-equivalent is HS256-signed with AUTH_SECRET (no extra env var). Access tokens auto-refresh on expiry; if refresh fails the chat inline-renders a Reconnect button.

Discovered tools appear under the server with a Test call button (admin for team servers, owner for personal). Tools are namespaced as mcp__<serverIdCompact>__<toolName> and merged into the agent's toolset on every /api/chat request. Outputs are fenced through fenceExternalContent so the agent treats them as untrusted data per Rule 8 of the system prompt. A background mcp-health worker pings every enabled server on a 5-minute schedule and surfaces last_connected_at / last_error in the UI.

Timeline as an MCP server (outbound)

Expose this Timeline as an MCP server so external agents (Claude Desktop, Cursor, web-based agents, etc.) can query team-level workspace context: events, entities, objects, tasks, boards, calendar, documents, and connected integration activity. Admins can open the Connections sidebar item (/app/team/integrations) and use Manage Timeline MCP endpoint, or go directly to /app/team/mcp-share:

  1. Open Connections (/app/team/integrations), choose Manage Timeline MCP endpoint, and copy the MCP endpoint URL shown there.
  2. Click New key, give it a label (e.g. "Claude Desktop — personal mac"), and copy the one-time plaintext.
  3. In the consuming agent, add an MCP server with:
    • URL: <your Timeline origin>/api/mcp/server
    • Header: Authorization: Bearer tla_...

Use Streamable HTTP / remote URL client settings, not legacy SSE. Timeline currently advertises MCP protocol 2024-11-05 during initialize and exposes a single HTTP JSON-RPC endpoint at /api/mcp/server. Methods: initialize, tools/list, tools/call, resources/list, resources/read, prompts/list, prompts/get. Tools exposed:

Codex CLI users can connect it with an environment-backed bearer token:

export TIMELINE_MCP_KEY="tla_..."
codex mcp add timeline --url "<copied MCP endpoint URL>" --bearer-token-env-var TIMELINE_MCP_KEY

Remote-MCP JSON clients can use the same endpoint and bearer key:

{
  "mcpServers": {
    "timeline": {
      "type": "streamable-http",
      "url": "<copied MCP endpoint URL>",
      "headers": {
        "Authorization": "Bearer tla_..."
      }
    }
  }
}

ChatGPT can create apps from remote MCP servers in Developer mode: Settings → Apps & Connectors → Advanced settings → Developer mode, then create an app/connector and use the copied MCP endpoint URL as the connector URL. OpenAI's ChatGPT app flow currently documents OAuth, no-auth, and mixed auth for created apps; Timeline's outbound endpoint currently uses static bearer keys, so a first-class ChatGPT connector needs an OAuth-backed auth path or bridge before it is a one-click setup.

  • timeline.retrieve_workspace_context — broad read-only retrieval across objects, notes, events, tasks, boards, calendar, documents, and route guides
  • timeline.search_events — semantic search across raw events
  • timeline.get_event / timeline.list_events — fetch + paginate
  • timeline.get_entity — lookup person / company / project / topic
  • timeline.get_object, timeline.search_objects, timeline.list_objects, timeline.list_tasks — read workspace objects and tasks
  • timeline.search_boards — read boards and matching board items
  • timeline.list_calendar_events, timeline.get_calendar_event, timeline.resolve_time_context — read calendar state and resolve date ranges
  • timeline.search_documents, timeline.search_documents_structured, timeline.get_document, timeline.get_document_chunk, timeline.list_recent_document_changes — search and inspect team documents
  • timeline.list_integrations, timeline.search_integration_events, timeline.get_integration_resource — inspect connected integrations and synced external-resource history

Isolation: bearer keys are team-scoped, not per-user. The handler runs all queries with a pseudo-zero-UUID actor so events with visibility=private or specific_users stay invisible to outbound clients — only visibility=team events flow out. Keys are stored as SHA-256 hashes (plaintext shown once at creation). Revoke from the same page; revocation is immediate.

Wildcard CORS is set so browser-based agents work; Authorization-header auth means cookies cannot authenticate the cross-origin call. When proxy IP headers are available, requests are rate-limited per IP at 600/min.

How sync runs

A BullMQ repeatable enqueues an integration-sync tick every 5 minutes. The worker fans out to enabled native team scopes that are due and runs incrementalSync() through the owning provider connection, using the per-resource cursor in integration_sync_state. Providers with inbound webhooks, such as Google Drive, can enqueue an extra one-shot incremental; GitHub selected repos and organization scopes are covered by the poller only. GitHub background sync skips active provider rate-limit pauses, waits at least an hour after the previous successful sync, and caches organization repo expansion for a short window so org-wide selections do not re-list every repository on every tick. GitHub repo cursors are also split by surface — PRs, issues, commits, releases, and workflow runs — so one failing or noisy surface does not block cursor advancement for the others. Releases and workflow runs poll less often than high-signal PR, issue, and commit surfaces. MCP servers are monitored by the MCP health worker, but that health check only validates connectivity and cached tools.

GitHub commit sync keeps a high-water SHA per repo. If a repo has more than the configured page window of new commits, the worker saves a commit-gap checkpoint and the next incremental run continues draining older commits instead of replaying the same page window forever. A first sync that starts with oversized commit history imports the newest window, records an audit row, and advances the high-water cursor so future polling stays current.

Manual full backfill from the CLI:

pnpm --filter @timeline/worker integration-resync -- --team=<uuid> --from-zero

Audit log

Every connect, sync start, sync finish, sync error, and replay writes a row in integration_audit_log. /app/team/integrations/audit renders the most recent 200 integration audit rows. Provider resource sharing and activation also write generic audit_log settings rows for team-level audit exports. The agent's list_integrations tool also surfaces connected providers + their last_synced_at.

Troubleshooting

Webhook returns bad_signature
Check the secret env var matches what the provider's webhook UI shows. The signing algorithm is HMAC-SHA256 over the raw body — make sure the provider hasn't re-serialised the JSON in transit.
Connect button stays disabled
The provider's OAuth client env pair is missing or empty. Set both CLIENT_ID and CLIENT_SECRET and restart.
Sync runs but no timeline events
The agent's dedup_key partial unique index makes replay a no-op. Use --from-zero on the resync script to wipe the cursor and re-walk from provider epoch.
