Native integrations & custom MCPs

SetupLast updated 2026-08-04

Connect native GitHub, Linear, Google Drive, Monday.com, Slack, and Sentry as personal provider accounts from /app/me/connections, share the sources a team may use, then activate team sync from /app/sources. Native providers sync external activity into the timeline as source='integration'. Team MCP servers in the Advanced integration tools section of /app/team/integrations give the agent live tool access; successful tool results are captured as private integration evidence for reconciliation, while passive provider activity still needs a native sync adapter or custom ingestion layer. For tools that only need to push arbitrary evidence into Timeline, admins can also create named ingest webhooks from /app/sources.

Encryption key (required first)

All integration auth (OAuth refresh + access tokens, bearer tokens, custom-header values, basic-auth credentials, MCP dynamic-client secrets) is encrypted at rest with AES-256-GCM in packages/shared/src/crypto/secrets.ts. Generate a 32-byte key and set SECRETS_ENCRYPTION_KEY in your environment: 

node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"

The first encryptSecret() call throws with a clear message if the key is missing or the wrong length, so worker boot fails fast instead of writing plaintext.

Native integration UI model

Native integrations have three separate layers. Provider account is the OAuth grant owned by the member who connected it. Shared sources are the boards, repositories, projects, drives, or channels that owner allows the current Timeline team to use. Team sync is the admin-selected import path that turns shared sources into timeline evidence.

A member can connect more than one provider account when the provider returns a different external account id. For providers that reuse the currently signed-in account, such as Monday.com in many browsers, start Connect account again and choose another account in the provider's OAuth account picker, or sign out/switch accounts in the provider before approving Timeline.

Disconnecting an active import stops that team's sync path. Deleting a provider account removes the member-owned OAuth grant and leaves affected teams with connection attention so an admin can reconnect, replace the source path, or pause the import intentionally.

Google Drive

Timeline uses a server-side OAuth web flow and requests Drive read-only access. Google scopes are requested by the authorize URL, but the OAuth consent screen must be configured for external/internal use before non-test users can connect.

  1. In Google Cloud Console → APIs & Services → Credentials, create an OAuth 2.0 client with type Web application.
  2. Under Authorized redirect URIs, add: https://thetimeline.cc/api/integrations/google_drive/callback. Authorized JavaScript origins are not used by Timeline's server-side callback flow.
  3. Enable the Google Drive API for the project.
  4. Ensure the OAuth consent screen allows these scopes: https://www.googleapis.com/auth/drive.readonly and https://www.googleapis.com/auth/drive.metadata.readonly.
  5. Copy the OAuth client id and client secret from the credential details page.
  6. Set: 
    GOOGLE_CLIENT_ID=...
GOOGLE_CLIENT_SECRET=...
# REQUIRED before accepting Drive webhooks. 32+ bytes of randomness.
GOOGLE_DRIVE_WEBHOOK_SECRET=...
  7. Restart the web + worker services. The provider appears in the native catalog when the required credentials are configured.
  8. Any team member can connect their Google Drive account from /app/me/connections or the native catalog. The member chooses whether their My Drive root or shared drives are shared with the current Timeline team.
  9. A team admin activates shared Drive sources from /app/sources.
  10. (Optional) Register a Drive push-notification channel for incremental sync. The channel token must be <integration_id>.<HMAC-SHA256(GOOGLE_DRIVE_WEBHOOK_SECRET, integration_id)>; route hits /api/webhooks/google-drive. The handler refuses inbound notifications when the secret is unset, and rejects bad signatures. Timeline records channel expirations in integration_webhook_subscriptions; when a manual Drive channel expires, the integration tick marks it webhook_degraded while changes-cursor reconciliation continues.

Linear

Timeline uses Linear OAuth plus an optional signed webhook. OAuth grants the connection owner read access; the team only activates Linear teams that owner shares.

  1. Create an OAuth application at linear.app/settings/api/applications.
  2. Redirect URI: https://thetimeline.cc/api/integrations/linear/callback.
  3. Grant the OAuth app the read scope.
  4. Copy the OAuth client id and client secret from the Linear application page.
  5. Set: 
    LINEAR_CLIENT_ID=...
LINEAR_CLIENT_SECRET=...
LINEAR_WEBHOOK_SECRET=...
  6. In Linear Settings → API → Webhooks, point the webhook at https://thetimeline.cc/api/webhooks/linear with the secret above.
  7. Any team member can connect Linear from /app/me/connections or the native catalog. The member chooses which Linear teams are shared with the current Timeline team.
  8. A team admin activates shared Linear teams from /app/sources.

GitHub

GitHub is a native Timeline integration. It is optional for non-engineering teams, but when connected it receives the same first-party treatment as Linear and Google Drive: person-owned OAuth, team source selection, audit rows, encrypted tokens, worker sync, and cited timeline events. Synced external work items can also map to task objects; visible task titles stay human-facing while provider IDs, issue keys, numbers, and URLs stay in integration metadata, aliases, or evidence.

  1. Create a GitHub App at github.com/settings/apps. For an organization-owned app, use the organization's Settings → Developer settings page instead. Timeline still uses the app's OAuth web flow for the connecting user, then mints installation access tokens for repository syncs when GITHUB_APP_ID and GITHUB_APP_PRIVATE_KEY are configured.
  2. Callback URL: https://thetimeline.cc/api/integrations/github/callback.
  3. Timeline requests scopes in the OAuth authorize URL, so there is no separate scope picker in GitHub's app settings. The requested scopes are repo and read:org.
  4. Grant repository read permissions for Contents, Issues, Pull requests, Actions, and Metadata. Missing Pull requests read access records a PR-surface partial sync on the /pulls endpoint while commits, issues, releases, and workflow runs continue to sync when readable. Timeline keeps the connection attention visible until that partial failure clears, so admins can reconnect or re-grant access without losing the other GitHub surfaces. Keep both Issues and Pull requests read access: Timeline captures ordinary issue comments, PR conversation comments, review summaries, and inline review comments.
  5. Copy the app Client ID, generate/copy a Client secret, copy the numeric App ID, and generate a private key. Store the PEM as a multiline secret or with literal \n escapes.
  6. Set: 
    GITHUB_APP_CLIENT_ID=...
GITHUB_APP_CLIENT_SECRET=...
GITHUB_APP_ID=...
GITHUB_APP_PRIVATE_KEY=...
GITHUB_WEBHOOK_SECRET=...
  7. Configure the GitHub webhook URL as https://thetimeline.cc/api/webhooks/github and use the same GITHUB_WEBHOOK_SECRET as the webhook secret. Timeline verifies X-Hub-Signature-256, stores X-GitHub-Delivery, and routes selected repo/org deliveries through webhook-delivery.
  8. Subscribe the GitHub App webhook to push, pull_request, pull_request_review, pull_request_review_comment, issues, issue_comment, release, and workflow_run. Timeline still reconciles selected repos slowly, but these events carry normal day-to-day activity and review conversation without waiting for the reconciliation tick.
  9. Any team member can connect GitHub from /app/me/connections or the native catalog. The member then chooses which repos or organizations are shared with the current Timeline team.
  10. A team admin activates shared sources from /app/sources. A GitHub organization scope means all repos in that org the connection owner can access, including future repos; choose individual repos instead for a fixed list.
  11. Selected GitHub sources still use slow reconciliation through the integration worker, but normal PR, issue, release, workflow, and push activity can arrive through signed webhooks first. When installation-token config is present, repo hydration uses the GitHub App installation quota instead of spending the connecting user's OAuth token quota.

Monday.com

Timeline uses monday.com's OAuth app flow, not a marketplace-only integration recipe. The app needs read scopes for boards, users, updates, WorkDocs, and account metadata so selected boards and docs can become cited Timeline evidence and provider budgets can be keyed by the monday account instead of the connecting user. It also needs webhook read/write access so Timeline can provision selected board webhooks automatically.

  1. Open monday.com Developer Center, create an app, and open its OAuth / Permissions settings.
  2. Add the redirect URI: https://thetimeline.cc/api/integrations/monday/callback.
  3. Add these OAuth scopes exactly: boards:read, users:read, updates:read, docs:read, account:read, webhooks:read, and webhooks:write. Timeline also sends the same space-separated scope list in the OAuth authorize URL.
  4. Copy the app's Client ID and Client Secret from the Basic Information / OAuth settings.
  5. Set: 
    MONDAY_CLIENT_ID=...
MONDAY_CLIENT_SECRET=...
MONDAY_WEBHOOK_SECRET=...
  6. Timeline provisions board webhooks automatically for activated board sources using https://thetimeline.cc/api/webhooks/monday?token=<MONDAY_WEBHOOK_SECRET>. The route verifies the token, echoes monday.com's challenge body during URL verification, persists board deliveries, and lets webhook-delivery process selected board targets. If the app lacks account:read, webhooks:read, or webhooks:write, Timeline skips provider-side webhook provisioning, keeps selected-resource reconciliation running, and raises reconnect attention for the connection owner after you add the scopes.
  7. Any team member can connect Monday.com from the native catalog. The member chooses which boards and WorkDocs are shared with the current Timeline team. Monday.com classic subitem boards are identified by monday's Board.type=sub_items_board and hidden from this picker because choosing the parent board already imports its subitems. A board is not hidden merely because its user-defined name begins with “Subitems of”.
  8. A team admin activates shared sources from /app/sources. The integration worker imports board schema, generic records, subitems, record updates, status changes, owners, column changes, and selected WorkDocs into cited timeline events. Activation, newly added selections, and retries with an unresolved sync error enqueue a historical backfill immediately and reconcile webhooks independently, so a webhook failure does not block older items. Classic subitem webhook payloads are routed through parentItemBoardId and hydrate against the selected parent board. Multi-level boards use monday's hierarchy_scope_config: "allItems" query so descendants at every supported depth are imported from the real board. Slow reconciliation remains responsible for missed deliveries, while selected WorkDocs reconcile through their own daily cursor. Agent retrieval resolves the visible provider- and selection-eligible event IDs in Postgres before semantic search, so historical helper-board events never consume the semantic result budget. Candidate filtering is capped at 10,000 visible events and reports truncation instead of issuing an unbounded sequence of vector searches.
  9. Timeline pins monday API version 2026-04. Board pagination cursors are treated as valid for at most 60 minutes. Boards that exceed one 10,000-item worker batch enqueue an immediate resource-targeted continuation after the current integration lock is released, so another worker can acquire the lock and drain the next page before that provider cursor expires. An already expired or provider-rejected cursor restarts that board safely. A failed or inaccessible board is recorded as a partial failure without preventing the remaining selected boards from syncing.

Slack workspace ingestion

Slack has two first-party modes. Slack conversations and capture handles direct agent chats, explicit notes and files, bound-channel capture, /ask, and /timeline join. Native workspace ingestion uses the same Slack app credentials but syncs selected channels as a passive integration with source='integration' and provider='slack'. Native Slack workspace ingestion is reconciliation-first for v1; the /api/slack/events route remains dedicated to interactive Slack conversations and capture.

  1. Configure the Slack app from Slack conversations and capture setup, including SLACK_CLIENT_ID, SLACK_CLIENT_SECRET, and SLACK_SIGNING_SECRET.
  2. Add the native ingestion redirect URI: https://thetimeline.cc/api/integrations/slack/callback.
  3. Ensure the bot scopes include the native-ingestion scopes: channels:read, channels:history, groups:read, groups:history, files:read, reactions:read, users:read, and users:read.email. The Slack setup page also lists the additional scopes/events needed for commands, DMs, reactions, and app mentions.
  4. Connect Slack from the native catalog, share selected channels from /app/me/connections, then activate them from /app/sources. Private channels require the bot to be present before Slack will expose history. The worker reconciles selected channels hourly and honors Slack Web API Retry-After responses as shared provider budget pauses instead of retrying per Timeline team.

Sentry native source

These credentials are separate from SENTRY_DSN. Timeline uses Sentry OAuth to read selected Sentry organizations/projects into Timeline; it does not change where Timeline reports its own application errors.

  1. In Sentry, open Account Settings → API → Applications and create an OAuth application for Timeline.
  2. Add the redirect URI: https://thetimeline.cc/api/integrations/sentry/callback.
  3. Sentry OAuth scopes are requested by Timeline in the authorize URL; the app page may not have a separate scope picker. Timeline requests org:read, project:read, event:read, event:admin, and team:read.
  4. Use a confidential/server-side OAuth app that exposes a client secret. If the page says Public Client and only shows a client id, that PKCE-only app is not compatible with the current Timeline provider until the Sentry adapter adds PKCE support.
  5. Copy the Client ID and Client Secret. Authorized JavaScript origins are not used by Timeline's server-side callback flow.
  6. Set: 
    SENTRY_INTEGRATION_CLIENT_ID=...
SENTRY_INTEGRATION_CLIENT_SECRET=...
  7. Connect Sentry from the native catalog, share selected projects from /app/me/connections, and activate them from /app/sources. Timeline imports issue updates, resolved issues, and releases as cited events; Sentry issues map to cited incident evidence.
  8. For Sentry issue alert, issue lifecycle, and release webhooks, point the Sentry integration webhook URL at https://thetimeline.cc/api/webhooks/sentry. Timeline verifies Sentry-Hook-Signature with SENTRY_INTEGRATION_CLIENT_SECRET, persists the delivery, and lets webhook-delivery process direct events or targeted reconciliation for the selected organization/project targets.

Native provider ownership

Native provider credentials are provider connections: they belong to the team member who completes OAuth, not to the Timeline team. The team owns only the active source scope it has chosen from the resources that owner shared. Non-owners cannot browse private provider resources that have not been shared with the team.

If a connection owner leaves the team, deletes a connection, or GitHub, Drive, Linear, Monday.com, Slack, or Sentry requires reconnecting, Timeline creates blocking connection attention. The Connections integration page shows a Needs attention section and row-level actions so admins can ask the owner to reconnect, replace a connection with another shared source, or narrow shared sources; the worker pauses only the affected sync path and keeps previously captured raw events.

Webhook provisioning failures use webhook_degraded attention instead of a blocking reconnect state. The Connections integration page shows it as a degraded webhook status rather than a red reconnect banner; selected-resource reconciliation remains active and admins can still run manual sync while the webhook issue is fixed.

Ingest webhooks

Ingest webhooks are named evidence-only sources for arbitrary provider payloads: JSON, XML, text, form bodies, or any other text-like content. They do not require a provider-specific schema and never become authoritative state by themselves. Accepted deliveries are normalized into reconciliation evidence before downstream extraction; the AI extraction pipeline can then turn them into facts, citations, embeddings, and approval proposals.

  1. Go to /app/sources as a team admin.
  2. Create a named webhook, for example Pipedrive webhook. Choose whether new events default to team-visible evidence or private evidence owned by the creating admin.
  3. Copy the one-time secret URL or bearer token. Plaintext credentials are shown once; stored credentials are SHA-256 hashes and can be rotated without changing the webhook source.
  4. Configure the third-party provider to send POST requests to the copied URL. Providers that cannot store the key in the URL can call /api/webhooks/ingest with Authorization: Bearer tli_....
  5. Keep proposal generation enabled when the source may contain task, date, object, or relationship evidence. Disable it when the source should only land searchable evidence. The worker checks the current setting again before processing queued proposal jobs.

The public endpoint rate-limits both authentication attempts and accepted deliveries, dedups identical same-day deliveries per webhook, redacts sensitive request headers from metadata, enforces the payload size cap while reading the request body, and rejects binary/multipart uploads for now. URLs in accepted payload text are normalized into non-authoritative link artifact evidence, and emails, phone numbers, and conservative labeled addresses are stored on source_metadata.contacts. Duplicate delivery replay repairs missing link evidence for the existing raw event; contact metadata is captured when the raw event is first accepted. Payload text is fenced as external content before extraction and proposal prompts, so sender-authored instructions remain evidence instead of agent instructions. Documents and rich files should still go through the document drive until binary webhook ingestion is intentionally designed.

Custom MCP servers (inbound)

Bring tools from any MCP-compatible server into the agent's toolset. Visit the Advanced integration tools section of /app/team/integrations (team catalog — admins only) or /app/me/mcp-servers (personal overlay — visible only to you, any member can add). MCP servers are queried on demand during chat; they are not passive ingestion jobs, but successful tool results are written as private source='integration', provider='mcp' evidence for later reconciliation. Pick an auth mode:

  • None — public MCP servers with no auth.
  • Bearer token — API keys / personal access tokens.
  • Custom header — arbitrary header name + value.
  • OAuth — server speaks the MCP OAuth dance; state JWT-equivalent is HS256-signed with AUTH_SECRET (no extra env var). Access tokens auto-refresh on expiry; if refresh fails the chat inline-renders a Reconnect button.

Discovered tools appear under the server with a Test call button (admin for team servers, owner for personal). Tools are namespaced as mcp__<serverIdCompact>__<toolName> and merged into the agent's toolset on every /api/chat request. Outputs are fenced through fenceExternalContent so the agent treats them as untrusted data per Rule 8 of the system prompt. A background mcp-health worker pings every enabled server on a 5-minute schedule and surfaces last_connected_at / last_error in the UI.

Timeline as an MCP server (outbound)

Expose this Timeline as an MCP server so external agents (Claude Desktop, Cursor, web-based agents, etc.) can query team-level workspace context: events, entities, objects, tasks, boards, calendar, documents, and connected integration activity. Admins can open the Connections sidebar item (/app/sources) and use Manage Timeline MCP endpoint, or go directly to /app/team/mcp-share:

  1. Open Connections (/app/sources), choose Manage Timeline MCP endpoint, and copy the MCP endpoint URL shown there.
  2. Click New key, give it a label (e.g. "Claude Desktop — personal mac"), and copy the one-time plaintext.
  3. In the consuming agent, add an MCP server with:
    • URL: <your Timeline origin>/api/mcp/server
    • Header: Authorization: Bearer tla_...

Use Streamable HTTP / remote URL client settings, not legacy SSE. Timeline currently advertises MCP protocol 2024-11-05 during initialize and exposes a single HTTP JSON-RPC endpoint at /api/mcp/server. Methods: initialize, tools/list, tools/call, resources/list, resources/read, prompts/list, prompts/get. Tools exposed:

Codex CLI users can connect it with an environment-backed bearer token:

export TIMELINE_MCP_KEY="tla_..."
codex mcp add timeline --url "<copied MCP endpoint URL>" --bearer-token-env-var TIMELINE_MCP_KEY

Remote-MCP JSON clients can use the same endpoint and bearer key:

{

    "timeline": {
      "type": "streamable-http",
      "url": "<copied MCP endpoint URL>",
      "headers": {
        "Authorization": "Bearer tla_..."
      }
    }
  }
}

ChatGPT can create apps from remote MCP servers in Developer mode: Settings → Apps & Connectors → Advanced settings → Developer mode, then create an app/connector and use the copied MCP endpoint URL as the connector URL. OpenAI's ChatGPT app flow currently documents OAuth, no-auth, and mixed auth for created apps; Timeline's outbound endpoint currently uses static bearer keys, so a first-class ChatGPT connector needs an OAuth-backed auth path or bridge before it is a one-click setup.

  • timeline.search_events — semantic search across raw events
  • timeline.search_moments, timeline.list_moments, timeline.get_moment — retrieve bundled timeline moments first, then expand to cited raw event evidence for audit; results include the versioned moment shape and stable row anchor IDs. timeline.get_moment should prefer returned raw event IDs, but supported deterministic moment IDs can be expanded directly through bounded or exact source-metadata lookup.
  • timeline.get_event / timeline.list_events — fetch + paginate

  • timeline.list_calendar_events, timeline.get_calendar_event, timeline.resolve_time_context — read calendar state and resolve date ranges
  • timeline.search_documents, timeline.search_documents_structured, timeline.get_document, timeline.get_document_chunk, timeline.list_recent_document_changes — search and inspect team documents
  • timeline.list_integrations, timeline.search_integration_events, timeline.get_integration_resource — inspect connected integrations and synced external-resource history

Isolation: bearer keys are team-scoped, not per-user. The handler runs all queries with a pseudo-zero-UUID actor so events with visibility=private or specific_users stay invisible to outbound clients — only visibility=team events flow out. Keys are stored as SHA-256 hashes (plaintext shown once at creation). Moment tools are built from that same visible event set and fence raw snippets as external content before returning them. Revoke from the same page; revocation is immediate.

Wildcard CORS is set so browser-based agents work; Authorization-header auth means cookies cannot authenticate the cross-origin call. When proxy IP headers are available, requests are rate-limited per IP at 600/min.

How sync runs

A BullMQ repeatable enqueues an integration-sync tick every 5 minutes. The worker fans out to enabled native team scopes that are due and runs incrementalSync() through the owning provider connection, using the per-resource cursor in integration_sync_state. Providers with inbound webhooks persist native deliveries first, then the webhook-delivery worker normalizes the matching team targets and enqueues either targeted sync work or a bounded catch-up fallback. Google Drive can still use webhooks as wake-up signals; GitHub, Linear, Monday.com, and Sentry now route protected deliveries through the shared delivery worker. GitHub repo deliveries, Monday item/board deliveries, and Sentry project deliveries hydrate only the affected selected resource. Sentry issue alert, issue lifecycle, and release payloads can also write direct events before the reconciliation pass. Provider rate-limit responses also create account/app budget pauses in integration_provider_budgets; the scheduler skips every matching integration until the provider retry time rather than retrying per Timeline team. GitHub selected repos and organization scopes can accept signed webhook deliveries, while slow reconciliation still covers missed events and backfill. GitHub background sync skips active provider rate-limit pauses, waits at least an hour after the previous successful sync, and caches organization repo expansion for a short window so org-wide selections do not re-list every repository on every tick. GitHub repo cursors are also split by surface — PRs, issues, issue comments, inline PR review comments, commits, releases, and workflow runs — so one failing or noisy surface does not block cursor advancement for the others. Releases and workflow runs poll less often than high-signal PR, issue, and commit surfaces. MCP servers are monitored by the MCP health worker, but that health check only validates connectivity and cached tools.

GitHub commit sync keeps a high-water SHA per repo. If a repo has more than the configured page window of new commits, the worker saves a commit-gap checkpoint and the next incremental run continues draining older commits instead of replaying the same page window forever. A first sync that starts with oversized commit history imports the newest window, records an audit row, and advances the high-water cursor so future polling stays current. Timestamped issue-comment and inline-review-comment syncs use a per-surface continuation: after a page cap, Timeline drains the bounded page work provisionally, then replays the mutable result set from page one until two full page traversals agree before it advances the timestamp cursor. The worker resumes ordinary page handoffs promptly, backs off a changing dense boundary for a bounded number of replay attempts, and preserves its checkpoint for later reconciliation. Rate-limited comment checkpoints resume as targeted work for that same comment surface when the provider's recorded retry time arrives, so an issue-comment retry cannot consume an inline-review checkpoint.

Manual full backfill from the CLI:

pnpm --filter @timeline/worker integration-resync -- --team=<uuid> --from-zero

Existing Monday connections that selected hidden helper boards can be repaired with the team-scoped command below. It is a dry-run unless --apply is present. The command reports identifiers and counts only, preserves historical raw events, removes invalid shares/selections/cursors/subscriptions, deprovisions any recorded provider-side helper-board webhooks before deleting their local state, and queues parent-board backfills after apply. Discovery covers both current provider-connection shares and direct legacy Monday integration selections, including orphan board cursors and webhook rows left after a selection was removed. Each successful provider webhook deletion is recorded immediately, making a partially failed cleanup safe to rerun without deleting the same remote webhook twice. Backfill and webhook-reconciliation follow-ups are also persisted independently; rerun the same apply command to retry a failed step while skipping any step already completed. Use the provider-connection owner's user UUID; that user must also be a team admin so the command can verify each stored board through monday before changing it. Direct integrations use their integration token. Boards omitted from an otherwise successful monday classification response are listed as missing under their credential source and treated as unverified. An apply refuses any unverified credential sources unless the operator explicitly adds --allow-unverified after reviewing the dry-run. 

pnpm repair:monday -- --env-file=/path/to/.env \
  --team-id=<team-uuid> --user-id=<admin-user-uuid>

pnpm repair:monday -- --env-file=/path/to/.env \
  --team-id=<team-uuid> --user-id=<admin-user-uuid> --apply

Audit log

Every connect, sync start, sync finish, sync error, and replay writes a row in integration_audit_log. /app/team/integrations/audit renders the most recent 200 integration audit rows. Provider resource sharing and activation also write generic audit_log settings rows for team-level audit exports. The agent's list_integrations tool also surfaces connected providers + their last_synced_at.

Troubleshooting

Need to verify live provider credentials without leaking secrets
Run pnpm canary:integrations -- --env-file=/path/to/.env. The canary prints only OK, WARN, or SKIP rows for OpenRouter, GitHub App auth, Sentry API access, Postmark API access, native OAuth authorize endpoints, and native webhook/signing secrets, followed by secret-safe next steps for any non-OK row. Use pnpm canary:integrations:strict -- --env-file=/path/to/.env when every row must be OK. Configured GitHub, Google Drive, Linear, Monday.com, Slack, and Sentry OAuth rows require both client id and client secret env vars to be present, then build the provider authorize URL and make a secret-free request to the provider, treating provider-side non-5xx responses as proof that the app registration is reachable. The Sentry API row uses SENTRY_AUTH_TOKEN, SENTRY_ORG, and SENTRY_PROJECT and expects the token to have project read access; the Sentry webhook-signature row uses SENTRY_INTEGRATION_CLIENT_SECRET. The Postmark API row uses POSTMARK_SERVER_TOKEN for a read-only server lookup; the inbound webhook row checks POSTMARK_WEBHOOK_SECRET. When POSTMARK_INBOUND_CANARY_TO and POSTMARK_INBOUND_CANARY_FROM are also configured, along with POSTMARK_INBOUND_CANARY_ALLOWED_ORIGIN matching the app origin, the canary posts a synthetic Postmark-shaped payload to /api/email/inbound and expects one raw event insert.
Need to exercise the Monday board contract against a dedicated canary board
Set MONDAY_CANARY_ACCESS_TOKEN and MONDAY_CANARY_BOARD_ID, then run the normal integration canary command. The read-only check verifies that the target is a real board and that all-depth item discovery is accepted. To also create and immediately delete a webhook, set MONDAY_CANARY_PROVISION_WEBHOOK=1; this additionally requires AUTH_URL and MONDAY_WEBHOOK_SECRET. Never point the canary at a production customer board or a classic helper board.
Webhook returns bad_signature
Check the secret env var matches what the provider's webhook UI shows. The signing algorithm is HMAC-SHA256 over the raw body — make sure the provider hasn't re-serialised the JSON in transit.
Connect button stays disabled
The provider's OAuth client env pair is missing or empty. Set both CLIENT_ID and CLIENT_SECRET and restart.
Sync runs but no timeline events
The agent's dedup_key partial unique index makes replay a no-op. Use --from-zero on the resync script to wipe the cursor and re-walk from provider epoch.
