Postmark email setup

SetupLast updated 2026-07-03

Postmark powers inbound timeline capture and outbound product emails.

Per-team email ingest. A team's address is <team-slug>@<INBOUND_EMAIL_DOMAIN>, populated automatically on team creation. Forward, CC, or BCC any mail to that address and it lands in the timeline. The same Postmark server token is also used to send transactional product emails.

1. Account + server

  1. Sign up at https://postmarkapp.com.
  2. Create a server named "Timeline".
  3. Copy the Server API Token.
POSTMARK_SERVER_TOKEN=...
SUPPORT_EMAIL=contact@thetimeline.cc

POSTMARK_SERVER_TOKEN is used by the shared messaging module for outbound transactional email: team invites, support/contact mail from /help/support, welcome email, email verification templates, daily digest delivery, and durable integration connection-attention notices. Set TRANSACTIONAL_EMAIL_FROM to the verified Postmark sender used in the From header. Existing deployments that still set only INVITE_EMAIL_FROM continue to use it as a compatibility fallback, but new environments should use TRANSACTIONAL_EMAIL_FROM. Set SUPPORT_EMAIL to the mailbox destination for support requests. Requests use the visitor's email as Reply-To. The inbound webhook is authenticated separately via POSTMARK_WEBHOOK_SECRET.

2. Outbound product email

  1. In Postmark, configure an outbound sender signature or verified domain.
  2. Set the sender address in the app environment.
TRANSACTIONAL_EMAIL_FROM="The Timeline <noreply@thetimeline.cc>"

Product email is sent through @timeline/shared/messaging, which records durable delivery rows before handing email to Postmark. Team settings sends invite emails after the invite row is committed. If Postmark is unavailable or these outbound env vars are missing, the invite is still created, the UI shows the send failure, and admins can copy the fallback invite URL or resend later. Signed-in recipients with a matching account email also see unexpired invites in the team switcher modal, where they can accept or decline without finding the email; email verification is not required to join.

Maintain HTML email templates as static files in packages/shared/src/messaging/email-templates. The shared package build copies them into dist/messaging/email-templates, so server actions and workers render the same branded templates in development and production. The web standalone build also copies that dist template directory into the standalone root and app subtree; invite, verification, support, and welcome server actions require those files at runtime. The worker uses the shared package's dist templates for daily digest email rendering.

Daily digests are personalized per active team member, generated against a 25-hour lookback window ending at the recipient's configured digest hour in their effective digest timezone, stored in daily_digests, and sent once per generated digest unless the recipient has disabled the digest in Team settings → Messaging. When a recipient has no explicit messaging preference row, the digest timezone comes from the team's workspace timezone. Quiet windows are stored as skipped and do not call the summarizer or enqueue an email. A digest is useful when the recipient has a visible event created or occurring since the previous configured local digest boundary, an object change (including an archive or merge), a new team member, a pending approval, or a calendar item in the next seven days. That fresh local cycle is normally 24 hours and follows daylight-saving changes without dropping or replaying activity. Unchanged open tasks do not appear as digest inventory and do not trigger delivery by themselves; the digest instead summarizes newly created or completed tasks and collapses repeating calendar series to one upcoming entry. The summarizer writes narrative prose for the overview and each section rather than listing pull requests or run IDs. Activity counts new moments, proposals, tasks, projects, and other objects in the window. The 25-hour evidence span preserves overlap on ordinary and spring-forward cycles and covers the complete 25-hour fall-back cycle; an already-seen event does not trigger another digest unless it arrived during the current fresh cycle. Events ingested after a cycle's boundary are deferred to the next cycle, while events created during the window still count even when their original occurrence time is older. Each generated digest covers all timeline events in its window (paginated, not capped), with every visible moment surfaced to the summarizer. Email and in-app digest use the same payload; the email CTA opens that day's row on Work → Digests. The worker registers the noon UTC scheduler on boot and also queues one idempotent catch-up tick, so a deploy or missed scheduler state still creates the current expected digest rows. In-app notifications remain inbox-only; digest email may summarize pending approvals and inbox state, but individual notification rows are not fanned out as standalone emails.

New signups receive a non-blocking verification email through the same messaging module. Unverified users can resend from the account menu; verification updates users.emailVerified but does not block app access.

Add the DNS records Postmark shows for thetimeline.cc: DKIM TXT, Return-Path CNAME, and a single SPF TXT record that includes include:spf.mtasv.net.

3. Inbound stream

  1. In the server, go to Inbound → set up an inbound stream.
  2. Set the inbound webhook URL to: 
    https://thetimeline.cc/api/email/inbound
  3. Enable Include raw email content in JSON payload.
  4. Set the Include attachments option to Yes.

4. Webhook authentication (Basic Auth)

We verify every inbound request via HTTP Basic Auth. Postmark sends the configured user/password in the Authorization header; the handler compares in constant time against POSTMARK_WEBHOOK_SECRET. 

openssl rand -hex 32

POSTMARK_WEBHOOK_SECRET=<the_hex_string>

In the Postmark dashboard, set the webhook URL with credentials embedded:

https://postmark:<the_hex_string>@thetimeline.cc/api/email/inbound

(Either user:secret or :secret is accepted; the secret can be in either position. The matched value must equal POSTMARK_WEBHOOK_SECRET exactly.)

Optional: source IP allowlist

Set POSTMARK_INBOUND_IPS to a comma-separated list of CIDRs (IPv4) to reject requests from outside Postmark's published webhook IP ranges before the basic-auth check. Failed-auth requests are also rate-limited per source IP (30/min) and return 429 once the bucket empties, so a credential-spray attack against the basic-auth header gets locked out fast. Leave unset in dev / staging to skip the IP check entirely. 

POSTMARK_INBOUND_IPS=3.134.147.250/32,50.31.156.6/32

5. Inbound email domain

Each team gets <team-slug>@<INBOUND_EMAIL_DOMAIN>. Configure MX records for that domain to point at Postmark. 

INBOUND_EMAIL_DOMAIN=in.thetimeline.cc

MX in inbound.postmarkapp.com 10

Teams created before Phase 7 are backfilled to <slug>@inbound.invalid. Run a one-off UPDATE teams SET inbound_email = slug || '@in.thetimeline.cc' if you need to flip a legacy team to the production domain.

6. Public contact mailboxes

contact@thetimeline.cc and hello@thetimeline.cc are public mailbox aliases, not timeline ingest addresses. Configure them in the domain's mail-routing provider to forward to the operator's personal inbox. When using Cloudflare Email Routing, keep the root-domain MX records on Cloudflare's mail servers and add routing rules for both aliases.

7. What gets ingested

For each inbound delivery the dispatcher:

  1. Parses the Postmark payload (Zod schema).
  2. Resolves which team(s) the message was addressed to via the Postmark mailbox hash or teams.inbound_email. Multiple recipients land as multiple rows, one per team.
  3. Applies the optional team sender whitelist. When enabled in Team settings, only exact normalized From email addresses from the saved whitelist are accepted. Blocked deliveries are dropped before attachment uploads, raw events, or queue work.
  4. Looks up the From address against users.email joined to team_members. Match → attributed to that user. No match → row lands with authorUserId=null and source_metadata.sender_unverified=true. Unverified senders are kept team-visible rather than inheriting private owner defaults.
  5. Strips quoted-reply chains for content_text; preserves the original TextBody / HtmlBody in source_metadata.raw_postmark so re-extraction can replay against the full thread.
  6. Parses forwarded-message chains from Gmail, Apple Mail, and Outlook-style headers. The first forwarded sender remains available as source_metadata.forwarded_from, while the ordered chain is stored as source_metadata.forwarded_chain[] with sender, recipients, subject, date, and body text. Forwarded bodies are included in content_text so extraction, embeddings, and suggestions can evaluate the thread instead of only the forwarder's intro.
  7. Parses In-Reply-To and References headers and links the row to its thread via source_metadata.thread_root_id.
  8. Routes attachments by content-type:
    • audio/* → timeline-audio bucket + a child raw_event + transcribe job.
    • Everything else → timeline-attachments bucket for raw attachment export and, when S3_BUCKET_DOCUMENTS plus REDIS_URL are configured, a captured document/version linked to the parent email raw event and queued for document extraction.
  9. Enqueues extract, embed, and approval-suggestion work for text-bearing parent events. Attachment-only deliveries wait for transcription or document extraction before any approval suggestion is created.
  10. Records emails, phone numbers, and conservative labeled addresses from the accepted email text on source_metadata.contacts. Accepted email/phone memory becomes person identity facets through reviewable object-memory paths.

Idempotency: a partial unique index on (team_id, source_metadata->>'message_id') makes Postmark retries silent no-ops.

8. Smoke test

Before sending a test email, run pnpm canary:integrations -- --env-file=/path/to/.env. The Postmark rows perform a read-only server lookup with POSTMARK_SERVER_TOKEN and verify that POSTMARK_WEBHOOK_SECRET is configured, without printing either secret.

To exercise the live inbound route without opening the Postmark dashboard, configure POSTMARK_INBOUND_CANARY_TO to a canary team's inbound address and POSTMARK_INBOUND_CANARY_FROM to a sender allowed by that team's inbound whitelist. Also set POSTMARK_INBOUND_CANARY_ALLOWED_ORIGIN to the exact trusted app origin, such as https://thetimeline.cc. The same canary command then posts a synthetic Postmark-shaped payload to /api/email/inbound, requires the app to report one inserted raw event, and polls DATABASE_URL for that exact raw_events.source='email' row. The script only sends the Basic-auth webhook secret when AUTH_URL matches that allowed HTTPS origin, except for localhost HTTP during development.

Postmark dashboard has a test inbound email feature. Send a test message; the app should write a raw_events row with source='email'. The timeline UI shows the subject + from header; the entity profile pages link the new event. If the body includes a valid email address or phone number, the raw event metadata should include the extracted contact value without creating a standalone artifact.
