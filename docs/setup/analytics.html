Analytics setup

SetupLast updated 2026-10-24

PostHog Cloud EU is the default product analytics and feature flag service.

PostHog counts public-site visitors, pageviews, referring sites, and popular pages. Product analytics use explicit lifecycle events. Session recording and automatic click capture are disabled; prompts, transcripts, filenames, and uploaded content are excluded.

Website traffic

Open PostHog Web analytics for visitors, pageviews, referrers, and popular pages. Collection starts with this deployment; earlier visits are not backfilled. Browser blockers can prevent collection.

The root layout mounts WebsiteAnalytics, which reuses the authenticated PostHog client and sends one $pageview per public pathname visit, including client-side navigation. Public paths come from the existing public-document registry, excluding machine documents, plus /sign-in and /sign-up. Workspace pages, invite/verification token paths, and unknown routes do not emit pageviews. Query-only changes and React rerenders do not add pageviews; returning to a public page after another route does.

The browser send hook removes query strings, fragments, campaign parameters, search terms, and page titles. Referrers retain only their HTTP(S) origin; private paths are removed from session and initial-person metadata, including both SDK person-property locations. Visitor and session identifiers remain available for counting. Session recording stays disabled, and the hook also rejects recording snapshots. Product-event tracking and team identification continue through the same client.

1. Project

  1. Create a PostHog Cloud EU project.
  2. Copy the project API key.
  3. Set the EU ingestion host.
NEXT_PUBLIC_POSTHOG_KEY=phc_...
NEXT_PUBLIC_POSTHOG_HOST=https://eu.i.posthog.com

Production web and main-worker services have these variables configured. Browser variables must also be present during the web build. The credential-thin document-extract service does not receive a PostHog key; document-upload analytics originate in the web service.

Production dashboard

The Launch dashboard uses explicit product events over the last 30 days:

On 2026-10-24, a synthetic analytics_configuration_verified event sent through the Node SDK with Railway's production configuration was confirmed in PostHog Activity. Its distinct ID starts with analytics-smoke-. It is a separate event and does not enter these product-event charts. Empty product charts are valid until real users perform the corresponding actions; the check does not establish end-to-end delivery from every deployed product action. Website traffic is collected separately through explicit $pageview events; automatic click capture and session replay remain disabled.

2. Events

The typed event map lives in packages/shared/src/analytics/events.ts. Every event has an owner, trigger, no-PII policy, and retention note. Add new events there before emitting them from web or worker code.

Allowed payloads: stable user/team/object IDs, enum-like sources/types/statuses, counts, durations, booleans, and model IDs. Disallowed payloads: emails, names, prompts, generated answers, transcripts, document text, filenames, cookies, auth headers, and uploaded content.

Approval analytics are action-grained: one successful single, revision, or bulk reviewer action emits one approval_decision_submitted event. The item count describes a bulk action; generated proposals and their individual internal lifecycle changes are not emitted as product events.

3. Feature flags

Feature flags are typed in the same analytics contract. Each flag must have an owner and a cleanup note. Do not leave feature flags as permanent configuration.
